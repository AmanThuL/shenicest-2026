# 契约：场景与资产所有权

> 谁能改哪个文件。**这是整个项目里唯一一条"不做就一定会丢工作"的规定。**
> 状态：D13 必须在开工第一天执行 · 最后修订 2026-08-24

---

## 为什么分工的单位是文件，不是模块

Unity 的 `.unity` 和 `.prefab` 是**不可手工合并的 YAML**。两个人同时改同一个场景，merge 的结果不是冲突标记，是丢工作。

所以协作纪律的核心不是"谁 own 哪个脚本"，而是**谁 own 哪个场景**，而且靠**拆场景**避免并发，不靠锁文件。

上层规则见 [`guidelines/11`](../../guidelines/11-scenes-prefabs-workflow.md) 第 1~3 条。

## D13 —— 场景必须拆两份

每个关卡至少拆成：

| 场景 | 内容 | owner |
|---|---|---|
| `Level00_Environment.unity` | 地形、倒木、枯树、草地、异色草带、灯光、APV、Volume、烘焙数据（**active scene**） | 场景美术 + 技术美术 |

**第一天就拆**，不要等冲突了再拆。

## gameplay 程序 ↔ 前端工程师（UI owner）

本节只覆盖这两个程序岗位之间的分工。技术美术、场景美术、UI 美术、主策划的归属见上面的[全项目所有权表](#全项目所有权表)，不在这两人之间的契约范围内。

| gameplay owner | UI owner |
|---|---|
| `Scripts/Runtime/` 除 `UI/` 外全部 | `Scripts/Runtime/UI/`（presenter） |
| `Scenes/Bootstrap.unity` | `Prefabs/UI/HUD.prefab` |
| `Level00_Gameplay.unity` | `Prefabs/UI/*.prefab` |
| `Prefabs/Characters/Player.prefab` | 将来的 `Scenes/MainMenu.unity` |
| `Data/Config`、`Investigation`、`Narrative`、`Levels` | — |
| `Input/RootsDance.inputactions` | — |

**必须先做的一步**：HUD **不能**直接搭在 `Bootstrap.unity` 里，要做成 `Prefabs/UI/HUD.prefab`，Bootstrap 只放一个实例。这样 UI owner 永远不需要打开 Bootstrap（`guidelines/11` 第 4 条：两个人都要改的东西必须做成 prefab）。少了这一步，两个 owner 每天都会撞 Bootstrap。

**两人之间的契约只有两样**，任何一方单方面改动都算破坏：

1. `Data/Events/` 里的频道资产；
2. 界面 prefab 上 presenter 依赖的控件（删控件或换组件类型 = 改接口）。

两者都列在 [UI 与前端契约](UI与前端契约.md) 里。代码层面的边界（`Scripts/Runtime/UI/` 只准 using `Core` + `Events`）同样在那份文档。

## 日常流程

- 各自开 task 分支，每天至少一次把 `develop` 合进自己分支（分支模型与命令见 [`guidelines/06`](../../guidelines/06-version-control.md)）。
- 提交场景 / prefab 前先处理 Overrides 下拉菜单：只 apply 自己 own 的 prefab，其余 revert。**永远不要不看列表就 Apply All。**
- 灯光和 NavMesh 只由 `<Level>_Environment` 的 owner 烘焙，且烘焙数据单独一个提交。
- 一个提交只动一个场景 / 一个 prefab，并在提交信息里点名。
- 文本类文件（`.cs` / `.md`）可以正常 merge，不受本文档的独占约束——但仍然按目录归属划分 review 责任。界面 prefab 是 YAML，走独占规则。
