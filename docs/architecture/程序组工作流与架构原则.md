# 程序组工作流与架构原则

> 团队协作与架构原则入口。具体实现事实见 [运行时架构说明书](运行时架构说明书.md)。
> 状态：切片 00 生效 · 最后修订 2026-08-24

## 1. 单向数据流

所有 gameplay 运行态按这个方向流动：

```text
玩家输入 / 触发器 / UI 请求
  -> IWorldCommand
  -> CommandQueue
  -> WorldState
  -> ScriptableObject 事件频道
  -> UI / 动画 / VFX / 音频
```

表现层绝不写真相层；交互层与表现层不直接通信。需要跨边界时，先看
[contracts/](contracts/) 有没有现有契约；没有就补契约，再写代码。

## 2. 契约先行

会被两个人或两个岗位同时依赖的东西必须先写成契约：

- 场景、prefab、ProjectSettings 的 owner 见 [场景与资产所有权](contracts/场景与资产所有权.md)。
- gameplay 程序驱动动画、shader、VFX 的接口见 [表现层驱动契约](contracts/表现层驱动契约.md)。
- 美术资产进入 Unity 的格式见 [美术资产交付规范](contracts/美术资产交付规范.md)。
- UXML 元素名、事件频道和 UI 代码边界见 [UI 与前端契约](contracts/UI与前端契约.md)。

契约类文档的改动需要契约双方同意，并在团队频道说明。

## 3. 测试边界

真相层是唯一默认写单元测试的地方：`WorldState`、`CommandQueue`、`IWorldCommand`
和纯 C# 判定函数。交互层和表现层靠试玩验收。

具体测试清单与新增测试规则见 [测试策略](decisions/测试策略.md)。

## 4. Unity 文件协作

Unity 的 `.unity` / `.prefab` / `.asset` 不手写、不手工 merge。需要多人改的东西先拆文件：

- Bootstrap 只放常驻服务和 prefab 实例。
- 关卡拆成 `_Environment` 与 `_Gameplay`。
- HUD 做成 prefab，不能直接搭在 Bootstrap 场景里。
- 每个提交尽量只动一个场景或一个 prefab。

## 5. 提交纪律

- 包增删、渲染设置、场景结构、架构文档分别独立提交。
- 移动或改名资产必须连 `.meta` 一起提交。
- 修改 D 编号规则时不复用编号，只在原条目下注明修订日期。
- 合入 `develop` 前至少跑 EditMode 测试；切片 00 当前闸门是 9 个 EditMode 测试全绿。
