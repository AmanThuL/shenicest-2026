# WhereTheRootsDance 运行时架构说明书

> 《Where the Roots Dance》运行时架构的最底层规则。所有其他架构文档都建立在这一份之上。
> 状态：已实现并通过编译与测试 · 最后修订 2026-08-24

本文只回答一件事：**运行时的数据往哪个方向流，谁能改什么。**
接口契约见 [`contracts/`](contracts/)，谁做哪个文件见 [场景与资产所有权](contracts/场景与资产所有权.md)，切片 00 的具体实现计划见 [切片 00 实施计划](systems/切片00_实施计划.md)。

## 1. 三层

```
[ 交互层 Interaction ]        [ 真相层 WorldState ]              [ 表现层 Presentation ]
 FirstPersonController         纯 C#，无 UnityEngine 依赖           XxxView 组件（Animator/Shader/VFX）
 InteractionRaycaster   ──命令──▶  探索 flags / 已采样 / 已识别  ──事件──▶  uGUI presenters
 TriggerVolume                 报告条目 / 手记条目                        AudioCue
 ToolUseController             CommandQueue 单点消费
 （只发命令，彼此不依赖）                                          （只订阅事件，彼此不依赖，绝不回写真相层）
```

| 层 | 职责 | 验收方式 |
|---|---|---|
| 交互层 | 把玩家操作翻译成命令 | 试玩 |
| 真相层 | 游戏唯一 ground truth，持有全部运行态 | **单元测试**（见 [测试策略](decisions/测试策略.md)） |
| 表现层 | 把事件呈现为玩家可见的画面 / 音效 / UI | 试玩 |

**D1（铁律）**：表现层绝不写真相层；交互层与表现层不直接通信；真相层单一 owner。
**D3**：跨系统通信用 ScriptableObject 事件通道（`guidelines/03` 第 5 条）；同一 feature 内部用普通 C# `event`；`UnityEvent` 只用于 prefab 上策划手连的响应。

### D3.1 —— 层由数据方向决定，不由技术决定

一个用 uGUI 搭出来的面板，如果它发命令，它就是**交互层**；如果它只订阅事件显示，它才是表现层。同一个界面 prefab 里两种都有也正常。

由此，**"回流"只有一种**：表现层写真相层。交互层发命令是正常的从左到右，不叫回流。

### D3.2 —— 会发命令的 UI 只 raise 频道，不 enqueue 命令

`WorldAccess` 在 `RootsDance.App`，UI 直接用它会破坏 `Scripts/Runtime/UI/` 只依赖 `Core` + `Events` 的边界。规矩：UI raise 一个 `VoidEventChannelSO`（例如结局的 `SubmitReportRequested`），由 gameplay 侧的一个监听器把它翻译成命令——那个监听器才是交互层组件。

```csharp
// UI 侧（前端工程师的文件）：按钮只喊一声
[SerializeField] private VoidEventChannelSO m_submitRequested;
m_submitButton.clicked += () => m_submitRequested.RaiseEvent();

// gameplay 侧（gameplay 程序的文件）：把喊声翻译成命令
private void OnSubmitRequested() => WorldAccess.Enqueue(new SubmitReportCommand(), this);
```

按钮就是个输入设备，跟键盘的 E 键、跟地上的 `TriggerVolume` 没有区别；把输入翻译成命令的代码不住在 UI 文件里。

## 2. 为什么不需要 tick，但需要队列

本作**没有连续数值推进**：世界状态只在玩家做出一次交互时离散改变一次。硬套 tick 循环会写一堆永远不跑的空转代码。

但**不能因此就直接改状态**。Unity 的 gameplay 回调全在主线程单线程执行，所以不存在真正的数据竞争（除非用 Job System 或自开线程），会咬人的是四类**顺序性**问题：

| # | 问题 | 缓解 |
|---|---|---|
| 1 | 初始化顺序：additive 加载时脚本执行顺序**逐场景整体应用**，跨场景 `Awake` 先后不受控；非激活物体的 `Awake` 要等激活才跑 | D9 |
| 2 | 事件重入 / 双触发：同一次交互在一帧内被处理两次，或事件处理器里再发同一事件 | D7 + 交互 busy 门 |
| 3 | Trigger 抖动：站在触发体边界反复 Enter/Exit | D8 |
| 4 | 物理时序：`OnTriggerEnter` 在 `FixedUpdate` 物理步里发，输入在 `Update` 里读，同帧顺序不定 | D7 + D12 |

**结论：不需要集中 tick 循环，但需要两个最小内核——单一真相 + 命令单点消费。**

## 3. 单一真相（D6）

`WorldState` 是纯 C# 对象，由 `GameBootstrap` 创建并持有，**不是** MonoBehaviour、**不是** ScriptableObject。

> 为什么不能是 SO：SO 在 Editor 里被运行时写入会持久化到 `.asset`（改完一次下次进 Play 还在，而且会进 git）。`guidelines/03` 第 8 条已经写了"SO 资产运行时只读"。

```csharp
// Core/WorldState.cs —— 无 UnityEngine 引用，可 EditMode 直接测
public sealed class WorldState : IWorldStateReader
{
    public bool RaiseFlag(string id)      // 幂等：第二次返回 false，什么都不做
    public bool AddReportEntry(ReportEntry entry)   // 幂等：按 entry.Id 去重
    public event Action<string> FlagRaised;
    public event Action<ReportEntry> ReportEntryAdded;
}
```

### D6.1 —— 只读接口（把 D1 变成编译器强制）

`GameBootstrap.WorldState` 与 `WorldAccess.State` 都只返回 `IWorldStateReader`（`HasFlag` / `Report` / `HasReportEntry` / `CountReportEntries` + 两个事件）。可写的 `WorldState` 只有两个地方拿得到：`GameBootstrap` 的私有字段，和 `CommandQueue.Drain` 的入参。

**结果：表现层和交互层拿不到写入口，"绝不回写真相层"是类型层面成立的，不是靠 review。**

### D6.2 —— 读取侧：pull once at bind, push after

- 常驻 UI **不 pull**。事件载荷里带齐它需要的数据（例如 `ReportUpdate.CategoryCount` 就是把"土壤样本：01"里的计数由 `GameBootstrap` 算好带过去）。
- 会被反复打开的面板（报告、手记）在 `OnEnable` 里用 `IWorldStateReader` 读一次当前状态铺满列表，之后订阅频道增量更新。
- **触发点是"绑定时"而不是"初始化时"**——面板每次打开都要重读，因为报告、手记这类界面可能被反复开关。

## 4. 命令单点消费（D7）

所有会改变真相层的请求（trigger 命中、交互确认、工具用完）**不直接改状态**，而是入队；每帧在**一个固定位置**（`GameBootstrap.LateUpdate`）排空队列。

```csharp
public sealed class CommandQueue
{
    public void Enqueue(IWorldCommand command)
    public void Drain(WorldState state)   // m_isDraining 防重入；
                                          // drain 期间入队的命令留到下一帧
}
```

这一条同时解决了 §2 的第 2 和第 4 类问题：物理步里发的 trigger 和 `Update` 里读的输入不再互相抢先，统一在 `LateUpdate` 结算；事件处理器里再发命令也不会递归。

**D12 —— Trigger 只登记、不执行。** `TriggerVolume.OnTriggerEnter` 里只做一件事：入队一条 `RaiseFlagCommand`。播无线电、关 HUD、改 ZoneProgress 全部由订阅频道的表现层做。

**D8 —— 幂等。** 每条命令必须可以安全执行多次。区域进入一律用一次性 flag，**不做 Exit 回滚**——这就是"反复进出触发体，无线电不重播"的实现方式。

**D9 —— 初始化顺序。**
- 只有 `GameBootstrap` 一个静态访问点（`guidelines/03` 第 7 条允许的唯一一个）。
- **禁止**在任何组件的 `Awake` 里跨对象取数据；跨对象引用统一在 `Start` 或更晚。
- 内容场景组件**订阅频道资产**而不是订阅真相层——资产总是存在，所以加载先后无关紧要。`GameBootstrap` 负责把真相层的 C# 事件泵到频道上。
- 事件订阅一律 `OnEnable` 订、`OnDisable` 退，成对出现。

## 5. 完整的环

```
UI / 交互 ──命令──▶ CommandQueue ──▶ WorldState ──事件──▶ 频道资产 ──▶ UI / 表现
                                          ▲
                            面板打开时 pull 一次（IWorldStateReader，只读）
```

## 6. Unity 场景协作后果

Unity 的 `.unity` / `.prefab` 是不可手工合并的 YAML，冲突域天然落在场景与 prefab 文件上。
所以协作纪律的重心不是"谁 own 哪个脚本"，而是**谁 own 哪个场景 / prefab**。

切片 00 的落地方式：

| 文件 | owner | 原因 |
|---|---|---|
| `Level00_Environment.unity` | 场景美术 / 技术美术 | 地形、灯光、Volume、APV、烘焙数据集中在这里 |
| `Level00_Gameplay.unity` | gameplay 程序 | 玩家、触发体、交互物、Cinemachine 相机集中在这里 |
| `Prefabs/UI/HUD.prefab` | UI owner | UI 可独立迭代，Bootstrap 只放一个实例 |

完整规则见 [场景与资产所有权](contracts/场景与资产所有权.md)。
