## 1. 核心决定（D2）

**真相层是唯一要写单元测试的地方。** 交互层和表现层靠试玩验收。

这不是偷懒，是运行时架构的直接推论：

| 层 | 为什么这样验收 |
|---|---|
| 真相层 | 纯 C#，无 `UnityEngine` 依赖，无场景、无 Play 模式。喂命令进去、检查状态出来，几十毫秒跑完。**是全项目唯一能被廉价、确定性地验证的部分。** |
| 交互层 | 验收标准是"手感对不对""提示出现的时机自然不自然"。这些没有正确答案可以断言，只能试玩。 |
| 表现层 | 同上，而且它的正确性定义在美术和策划手里，不在程序手里。 |

推论：**把值得验证的逻辑挤进真相层。** 一条规则如果写在 MonoBehaviour 里就测不了，写成纯 C# 就能测——这是设计时的取舍依据，不是事后补测试的借口。

## 3. 什么时候必须加测试

**MUST**：任何新的 `IWorldCommand` 实现、任何 `WorldState` 上的新方法、任何"第二次做会不会出问题"的规则。
**SHOULD**：解谜条件判定（"集齐三条线索才开门"这类），一律写成纯 C# 判定函数放进 `Core/`，然后测它。
**不需要**：MonoBehaviour 的接线、UI presenter、交互距离参数、移动手感、任何需要场景才能跑起来的东西。

判断标准一句话：**如果这条规则错了，玩家会卡关或者数据会脏，那它就该在真相层，也该有测试。**

## 4. PlayMode 测试的定位

`RootsDance.Tests.PlayMode` 的 asmdef 已经存在但目前是空的，这是**有意的**。

PlayMode 测试要开场景、要等帧、跑一次几十秒，性价比远低于 EditMode。只在一种情况下才值得写：**一条跨越加载时序的 bug 反复出现**（例如"从关卡场景直接按 Play 时 bootstrap 晚一帧到达"这类）。到那时写一条 PlayMode 回归测试把它钉死，而不是提前铺一套。

注意 `BootstrapLoader` 在每次 PlayMode 测试运行时也会跑（Test Runner 生成的 `InitTestScene*` 是非 bootstrap 场景），所以 PlayMode 测试总是在 `Bootstrap.unity` 已加载、`GameBootstrap` 处于 adopt 模式的前提下执行。写的时候要按这个前提写。

## 5. 怎么跑

Editor 里：*Window > General > Test Runner > EditMode > Run All*。

命令行（CI 与提交前自检）：

```bash
/Applications/Unity/Hub/Editor/6000.3.22f1/Unity.app/Contents/MacOS/Unity -batchmode -nographics -runTests -testPlatform EditMode -projectPath . -testResults ./edit-tests.xml -logFile ./unity-tests.log
```

结果在 `edit-tests.xml`（NUnit 格式，根节点的 `total` / `passed` / `failed` 就够看）。`unity-tests.log` 里 `grep "error CS"` 为空才算编译干净。

**合并到 `develop` 之前这条必须是绿的。** 这是目前唯一的自动化闸门。
